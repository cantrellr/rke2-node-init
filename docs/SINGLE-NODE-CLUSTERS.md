# Production-style single-node RKE2 clusters

This repository supports single-node RKE2 clusters for test, development, edge-style labs, and replacement clusters that need production-style guardrails without running a full HA control plane. The implementation extends the existing `rkeprep/v2` image, registry, server, verify, and YAML conventions. It does not fork the supply-chain process.

## Executive position

A single-node RKE2 cluster is operationally useful, but it is not highly available. The control plane, embedded etcd, kubelet, workloads, and local snapshots all share one failure domain. If the node is down, the cluster is down. That is the business reality; do not dress it up as HA.

For production-like test and development use, the objective is to make the node deterministic, secure, recoverable, and cheap to operate. The objective is not to simulate quorum or rolling availability. Multi-node and single-node clusters should still use the same artifact staging discipline, the same offline registry expectations, and the same YAML-driven provisioning posture.

## rkeprep/v2 single-node kinds

Single-node manifests use explicit kinds so the operator does not have to infer behavior from optional YAML blocks.

| Kind | Process |
| --- | --- |
| `singleNodeImage` | Prepare a single-node golden image by delegating to the existing image action. |
| `singleNodeServer` | Apply the single-node overlay, then delegate to the existing server action. |

The current kind-driven entrypoint for these new kinds is:

```bash
sudo bash bin/rke2-single-node-profile.sh -f <single-node-yaml> -y
```

That helper keeps the single-node contract explicit while reusing the existing `bin/rke2nodeinit.sh image` and `bin/rke2nodeinit.sh server` implementation under the hood.

## What changed

| Area | Multi-node path | Single-node path |
| --- | --- | --- |
| Golden image | `bin/rke2nodeinit.sh image` or `airgap` | `kind: singleNodeImage` through `bin/rke2-single-node-profile.sh -f <yaml>` |
| Registry push | `bin/rke2nodeinit.sh push` | Same |
| Server provisioning | `bin/rke2nodeinit.sh server` or `add-server` | `kind: singleNodeServer` through `bin/rke2-single-node-profile.sh -f <yaml>` |
| Agent provisioning | `bin/rke2nodeinit.sh agent` | Not used unless the cluster intentionally grows later |
| RKE2 config | Base `/etc/rancher/rke2/config.yaml` generated by existing script | Base config plus `/etc/rancher/rke2/config.yaml.d/20-single-node-production.yaml` |
| Add-ons | Packaged components use RKE2 defaults unless overridden | Low-resource `HelmChartConfig` manifests for CoreDNS, Metrics Server, and Snapshot Controller |
| Security | Existing repo hardening and offline controls | Existing controls plus CIS profile, secrets-at-rest encryption, audit sizing, strict kubeconfig mode, snapshots, and default network policy |

The single-node helper dispatches `singleNodeImage` and `singleNodeServer`. For `singleNodeServer`, it applies the single-node overlay first, then delegates to the existing `bin/rke2nodeinit.sh server` action. This keeps the current provisioning engine in charge of hostname, networking, CA, tokens, artifact staging, and RKE2 installation while preventing the operator from forgetting the overlay step.

## Recommended generic flow

### 1. Build or refresh the golden image

Run this on the connected template VM or artifact-builder host.

```bash
sudo bash bin/rke2-single-node-profile.sh -f configs/single-node/golden-image.yaml -y
```

Equivalent explicit form:

```bash
sudo bash bin/rke2-single-node-profile.sh image -f configs/single-node/golden-image.yaml -y
```

For a VM template workflow that should shut down instead of rebooting, continue using the base `airgap` action explicitly until an equivalent single-node airgap kind is added:

```bash
sudo bash bin/rke2nodeinit.sh airgap -f configs/single-node/golden-image.yaml -y
```

### 2. Provision the single-node server

Use the kind-driven helper wrapper instead of calling `bin/rke2nodeinit.sh server` directly.

```bash
sudo bash bin/rke2-single-node-profile.sh -f configs/single-node/production-server.yaml -y
```

Equivalent explicit form:

```bash
sudo bash bin/rke2-single-node-profile.sh server -f configs/single-node/production-server.yaml -y
```

Equivalent expanded flow:

```bash
sudo bash bin/rke2-single-node-profile.sh apply -f configs/single-node/production-server.yaml
sudo bash bin/rke2nodeinit.sh server -f configs/single-node/production-server.yaml -y
```

The helper writes:

- `/etc/rancher/rke2/config.yaml.d/20-single-node-production.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-metrics-server-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-snapshot-controller-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/single-node-default-deny-ingress.yaml`

It also prepares host prerequisites for the RKE2 CIS profile where possible by creating the host `etcd` user/group and installing the RKE2 CIS sysctl drop-in if the staged RKE2 files are already present.

### 3. Verify the node

```bash
sudo bash bin/rke2-single-node-profile.sh verify
sudo bash bin/rke2nodeinit.sh verify -f configs/single-node/production-server.yaml
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get nodes -o wide
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get pods -A
sudo rke2 etcd-snapshot ls
sudo rke2 secrets-encrypt status
```

## COTPA single-node replacement cluster flow

The COTPA single-node configuration lives under:

```text
configs/cotpa-single-nodes/
├── image-hyperv-v1.35.5+rke2r2-singlenode.yaml   # kind: singleNodeImage
└── nodes/
    ├── dc1manager.yaml                           # kind: singleNodeServer
    ├── dc1domain.yaml                            # kind: singleNodeServer
    ├── dc2domain.yaml                            # kind: singleNodeServer
    └── dc3domain.yaml                            # kind: singleNodeServer
```

These are replacement clusters, so the node IPs intentionally reuse the existing replacement addresses:

| Cluster | Node manifest | Primary IP | Secondary IP | Cluster CIDR | Service CIDR | Cluster DNS |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `dc1manager` | `configs/cotpa-single-nodes/nodes/dc1manager.yaml` | `172.16.15.101` | `172.16.210.101` | `10.101.0.0/16` | `10.1.0.0/16` | `10.1.0.10` |
| `dc1domain` | `configs/cotpa-single-nodes/nodes/dc1domain.yaml` | `172.16.15.102` | `172.16.210.102` | `10.102.0.0/16` | `10.1.0.0/16` | `10.1.0.10` |
| `dc2domain` | `configs/cotpa-single-nodes/nodes/dc2domain.yaml` | `172.16.15.103` | `172.16.210.103` | `10.103.0.0/16` | `10.1.0.0/16` | `10.1.0.10` |
| `dc3domain` | `configs/cotpa-single-nodes/nodes/dc3domain.yaml` | `172.16.15.104` | `172.16.210.104` | `10.104.0.0/16` | `10.1.0.0/16` | `10.1.0.10` |

Build the image:

```bash
sudo bash bin/rke2-single-node-profile.sh -f configs/cotpa-single-nodes/image-hyperv-v1.35.5+rke2r2-singlenode.yaml -y
```

The COTPA `singleNodeImage` manifest uses scalar CSV for image-level DNS so the base image action logs and applies the intended values:

```yaml
spec:
  defaultDns: 172.16.10.11,172.16.10.12
  defaultSearchDomains: k8.cantrellcloud.net,cantrellcloud.net
```

Node-level interface DNS inside `singleNodeServer` manifests can still use YAML list syntax.

Provision each replacement cluster with the kind-driven wrapper:

```bash
sudo bash bin/rke2-single-node-profile.sh -f configs/cotpa-single-nodes/nodes/dc1manager.yaml -y
sudo bash bin/rke2-single-node-profile.sh -f configs/cotpa-single-nodes/nodes/dc1domain.yaml -y
sudo bash bin/rke2-single-node-profile.sh -f configs/cotpa-single-nodes/nodes/dc2domain.yaml -y
sudo bash bin/rke2-single-node-profile.sh -f configs/cotpa-single-nodes/nodes/dc3domain.yaml -y
```

The COTPA image manifest keeps `bootService.enabled: false` on purpose. The current first-boot service path runs the base `rke2nodeinit.sh` server workflow directly. For single-node clusters, that would bypass the single-node overlay. Use the wrapper command above unless and until the core boot service dispatcher is extended to call the wrapper for `kind: singleNodeServer`.

## YAML contract

Single-node manifests keep using `apiVersion: rkeprep/v2`, but now use explicit kinds:

```yaml
apiVersion: rkeprep/v2
kind: singleNodeServer
metadata:
  name: rke2-single01
spec:
  clusterMode: single-node
  singleNode:
    enabled: true
    mode: production
    enableCIS: true
    lowResourceAddons: true
    defaultNetworkPolicy: true
    ingressController: none
    snapshotScheduleCron: "0 */6 * * *"
    snapshotRetention: 12
    snapshotDir: /var/lib/rancher/rke2/server/db/snapshots
    auditLogMaxAge: 30
    auditLogMaxBackup: 10
    auditLogMaxSize: 100
```

`kind: singleNodeServer` is the explicit dispatch contract. `spec.clusterMode` and `spec.singleNode.enabled` remain in the manifest as defensive intent markers and backward-compatible opt-ins for render/apply workflows.

### `spec.clusterMode`

Supported values:

- `single-node` for one-node clusters.
- Omit the key for legacy multi-node behavior.

### `spec.singleNode.enabled`

When `true`, the single-node helper is allowed to apply the overlay. Without this opt-in, the helper exits unless `kind: singleNodeServer` or `--force` is used. That prevents an operator from accidentally applying single-node assumptions to a multi-node server.

### `spec.singleNode.mode`

| Mode | Intent | Defaults |
| --- | --- | --- |
| `production` | Long-lived test/dev clusters with production-like guardrails | CIS profile, compressed snapshots every 6 hours, 12 retained snapshots, audit retention 30 days |
| `dev` | Disposable, lower-resource engineering clusters | Same security posture, lower snapshot and audit retention when configured in YAML |

### `spec.singleNode.enableCIS`

When enabled, the overlay sets:

```yaml
profile: "cis"
protect-kernel-defaults: true
```

The helper also creates the local `etcd` user/group and attempts to install the RKE2 CIS sysctl file. If the sysctl source is not present yet, rerun the helper after image staging and before first `rke2-server` start.

### `spec.singleNode.lowResourceAddons`

When enabled, the helper writes RKE2 `HelmChartConfig` resources for CoreDNS, Metrics Server, and Snapshot Controller with conservative requests and limits. This keeps the baseline footprint low without tuning Kubernetes static control-plane pods blindly.

### `spec.singleNode.ingressController`

Default is `none`. That is deliberate. For a development single-node cluster, ingress should be a conscious choice because it changes the attack surface and consumes resources. If ingress is needed, set the value explicitly and pass `--enable-ingress` to the helper.

## Render-only mode

Use render mode to inspect the exact RKE2 overlay before writing it.

```bash
bash bin/rke2-single-node-profile.sh render -f configs/single-node/production-server.yaml
bash bin/rke2-single-node-profile.sh render -f configs/cotpa-single-nodes/nodes/dc1manager.yaml
```

This is useful in pull requests and troubleshooting because it shows the configuration RKE2 will read after the base `config.yaml` from `bin/rke2nodeinit.sh`.

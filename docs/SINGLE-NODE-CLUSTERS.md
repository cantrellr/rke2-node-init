# Production-style single-node RKE2 clusters

This repository now has an explicit single-node cluster path for test and development environments that still need a production-style security posture. The operating model is intentionally not a new lifecycle. It extends the existing `rkeprep/v2` image, registry, server, verify, and boot ISO flow with a small RKE2 config drop-in and low-resource packaged-component overrides.

## Executive position

A single-node RKE2 cluster is useful for platform validation, edge-style development, CI labs, demos, and isolated engineering sandboxes. It is not highly available. The control plane, embedded etcd, kubelet, workloads, and local snapshots all share one failure domain. If the node dies, the cluster is down. That is the trade-off; pretending otherwise is bad engineering governance.

For production-like testing, the goal is to make the node secure, deterministic, recoverable, and cheap to run. The goal is not to simulate HA. Multi-node and single-node clusters should use the same repo, same artifact staging discipline, same registry mirroring contract, and the same YAML-driven provisioning posture.

## What changed

| Area | Multi-node path | Single-node path |
| --- | --- | --- |
| Golden image | `bin/rke2nodeinit.sh image` or `airgap` | Same |
| Registry push | `bin/rke2nodeinit.sh push` | Same |
| Server provisioning | `bin/rke2nodeinit.sh server` or `add-server` | `bin/rke2-single-node-profile.sh apply`, then `bin/rke2nodeinit.sh server` |
| Agent provisioning | `bin/rke2nodeinit.sh agent` | Not used unless the cluster intentionally grows later |
| RKE2 config | Base `/etc/rancher/rke2/config.yaml` generated by existing script | Base config plus `/etc/rancher/rke2/config.yaml.d/20-single-node-production.yaml` |
| Add-ons | Packaged components use RKE2 defaults unless overridden | Low-resource `HelmChartConfig` manifests for CoreDNS, Metrics Server, and Snapshot Controller |
| Security | Existing repo hardening and offline controls | Existing controls plus CIS profile, secrets-at-rest encryption, audit sizing, strict kubeconfig mode, snapshots, default network policy |

## Recommended flow

### 1. Build or refresh the golden image

Run this on the connected template VM or artifact-builder host.

```bash
sudo bash bin/rke2nodeinit.sh image -f configs/single-node/golden-image.yaml -y
```

For a VM template workflow that should shut down instead of rebooting:

```bash
sudo bash bin/rke2nodeinit.sh airgap -f configs/single-node/golden-image.yaml -y
```

This remains the same workflow used by multi-node clusters. Do not fork golden images just because the target cluster has one node. Keep the supply-chain workflow consolidated.

### 2. Apply the single-node overlay before first server start

Run this on the target VM after the golden image is cloned and before `rke2-server` starts for the first time.

```bash
sudo bash bin/rke2-single-node-profile.sh apply -f configs/single-node/production-server.yaml
```

The helper writes:

- `/etc/rancher/rke2/config.yaml.d/20-single-node-production.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-metrics-server-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/rke2-snapshot-controller-config.yaml`
- `/var/lib/rancher/rke2/server/manifests/single-node-default-deny-ingress.yaml`

It also prepares host prerequisites for the RKE2 CIS profile where possible by creating the host `etcd` user/group and installing the RKE2 CIS sysctl drop-in if the staged RKE2 files are already present.

### 3. Provision the RKE2 server with the existing engine

```bash
sudo bash bin/rke2nodeinit.sh server -f configs/single-node/production-server.yaml -y
```

The original `server` action still owns hostname, static networking, registry trust, tokens, artifacts, install execution, and output capture. The single-node helper only supplies drop-in RKE2 configuration and low-resource add-on manifests.

### 4. Verify the node

```bash
sudo bash bin/rke2-single-node-profile.sh verify
sudo bash bin/rke2nodeinit.sh verify -f configs/single-node/production-server.yaml
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get nodes -o wide
sudo /var/lib/rancher/rke2/bin/kubectl --kubeconfig /etc/rancher/rke2/rke2.yaml get pods -A
sudo rke2 etcd-snapshot ls
sudo rke2 secrets-encrypt status
```

## YAML contract

Single-node manifests keep using `apiVersion: rkeprep/v2` and `kind: Server`. The new opt-in contract is under `spec.clusterMode` and `spec.singleNode`.

```yaml
apiVersion: rkeprep/v2
kind: Server
metadata:
  name: rke2-single01
spec:
  clusterMode: single-node
  singleNode:
    enabled: true
    mode: production
    enableCIS: true
    lowResourceAddons: true
    defaultNetworkPolicy: true
    ingressController: none
    snapshotScheduleCron: "0 */6 * * *"
    snapshotRetention: 12
    snapshotDir: /var/lib/rancher/rke2/server/db/snapshots
    auditLogMaxAge: 30
    auditLogMaxBackup: 10
    auditLogMaxSize: 100
```

### `spec.clusterMode`

Supported values:

- `single-node` for one-node clusters.
- Omit the key for legacy multi-node behavior.

### `spec.singleNode.enabled`

When `true`, the single-node helper is allowed to apply the overlay. Without this opt-in, the helper exits unless `--force` is used. That prevents an operator from accidentally applying single-node assumptions to a multi-node server.

### `spec.singleNode.mode`

| Mode | Intent | Defaults |
| --- | --- | --- |
| `production` | Long-lived test/dev clusters with production-like guardrails | CIS profile, compressed snapshots every 6 hours, 12 retained snapshots, audit retention 30 days |
| `dev` | Disposable, lower-resource engineering clusters | Same security posture, lower snapshot and audit retention |

### `spec.singleNode.enableCIS`

When enabled, the overlay sets:

```yaml
profile: "cis"
protect-kernel-defaults: true
```

The helper also creates the local `etcd` user/group and attempts to install the RKE2 CIS sysctl file. If the sysctl source is not present yet, rerun the helper after image staging and before first `rke2-server` start.

### `spec.singleNode.lowResourceAddons`

When enabled, the helper writes RKE2 `HelmChartConfig` resources for CoreDNS, Metrics Server, and Snapshot Controller with conservative requests and limits. This keeps the baseline footprint low without tuning Kubernetes static control-plane pods blindly.

### `spec.singleNode.ingressController`

Default is `none`. That is deliberate. For a development single-node cluster, ingress should be a conscious choice because it changes the attack surface and consumes resources. If ingress is needed, set the value explicitly and pass `--enable-ingress` to the helper.

## Render-only mode

Use render mode to inspect the exact RKE2 overlay before writing it.

```bash
bash bin/rke2-single-node-profile.sh render -f configs/single-node/production-server.yaml
```

This is useful in pull requests and troubleshooting because it shows the configuration RKE2 will read after the base `config.yaml` from `bin/rke2nodeinit.sh`.

## Low-resource defaults

The single-node profile keeps add-on requests intentionally small:

| Component | CPU request | Memory request | CPU limit | Memory limit |
| --- | ---: | ---: | ---: | ---: |
| CoreDNS | `25m` | `64Mi` | `100m` | `128Mi` |
| Metrics Server | `25m` | `64Mi` | `100m` | `128Mi` |
| Snapshot Controller | `10m` | `32Mi` | `50m` | `96Mi` |

Do not over-optimize the control plane itself until the node is measured under representative workload. Starving etcd or kube-apiserver creates ugly failure modes and false negatives during platform testing.

## Security baseline

Single-node does not mean soft target. The baseline is:

- Use a pinned RKE2 version and mirror all required images to the private registry.
- Keep `disableDefaultRegistryEndpoint: true` for strict offline behavior.
- Use `systemDefaultRegistry` so RKE2 system images resolve internally.
- Keep `write-kubeconfig-mode: "0600"`.
- Enable `profile: cis` and satisfy host-level prerequisites before first start.
- Keep `tls-san-security: true` and explicitly list node DNS/IP SANs.
- Enable secrets-at-rest encryption and record the rotation procedure.
- Keep compressed etcd snapshots and copy them off-node if the cluster matters.
- Start with no packaged ingress controller unless the workload requires it.
- Apply namespace network policies for anything beyond the default namespace.
- Patch default service accounts to avoid automatic token mounting in operator-created namespaces.

## Recovery and lifecycle

A single-node cluster has one recovery contract: snapshots plus rebuild discipline.

Minimum operating rhythm:

```bash
sudo rke2 etcd-snapshot save --name pre-change-$(date +%Y%m%d%H%M%S)
sudo rke2 etcd-snapshot ls
sudo rke2 secrets-encrypt status
```

Before major upgrades, certificate changes, registry changes, CNI changes, or secrets-encryption rotation, take an on-demand snapshot and copy it off-node.

For restoration, use the standard RKE2 snapshot restore flow on a rebuilt node with the same RKE2 version and the same private registry reachability. Keep node manifests, generated config overlays, registry CA, bootstrap token material, and snapshots together in your operational evidence package.

## Migration path to multi-node

Do not mutate a single-node dev cluster into an HA cluster casually. It is safer to promote the manifest pattern and rebuild as multi-node than to keep layering exceptions.

Recommended migration path:

1. Keep the golden-image and registry artifacts.
2. Copy shared fields from `configs/single-node/production-server.yaml` into the multi-node server manifest set.
3. Remove `spec.clusterMode: single-node` and the `spec.singleNode` block.
4. Use `server` for the first control-plane node and `add-server` for additional control-plane nodes.
5. Use `agent` for workers.
6. Re-evaluate snapshot schedules, PodDisruptionBudgets, storage, ingress, monitoring, and failure-domain labels.

## Hard stop criteria

Use a multi-node cluster instead of this profile when any of the following is true:

- The workload has uptime commitments.
- The cluster is a shared platform dependency.
- Multiple engineers or teams depend on it simultaneously.
- It hosts persistent data that cannot be rebuilt quickly.
- It needs rolling upgrades without downtime.
- It is exposed to untrusted networks.

Single-node is a cost-optimized engineering pattern, not an HA architecture. Keep that line bright.
